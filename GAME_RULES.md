# Territory Run — Proposed Game Rules

**Status:** Product proposal for review. No rules in this document are Product-approved. The current server verifier already enforces the provisional 50 m closure, 100 m path distance, and 50 m² area values. Those constants must not be treated as final release requirements until the decisions below are accepted.

## Game loop

Planned runs and free runs should use the same server-side activity lifecycle. A planned run gives a target distance and route suggestions; it does not grant a claim for following a suggested line. A free run is analyzed from its complete recorded GPS trace after stop. Both modes submit evidence, receive a pending/rejected/processed result, and can mutate territory only after server validation. The current suggestion endpoint synthesizes routes and the mobile route cards do not select or navigate a route, so planned-run behavior is not complete.

The first reliable territory mechanic should be a first claim from one valid closed loop. Attacks remain disabled until claim processing, spatial conflicts, and persistence are verified. Repeated/parallel paths and strengthening are proposed as later progression over an existing claimable area; the current code does not implement either mechanic.

## Proposed v0 validation and progression rules

| Rule | Proposed behavior and rationale | Edge cases and security | Acceptance criteria | Product decision still needed |
|---|---|---|---|---|
| Planned versus free activity | Record and validate the full trace for either mode. A target distance is a planning hint, not a client-supplied reward multiplier. A suggested route is advisory until route selection and navigation are real. This keeps reward authority on the server. | A user may deviate from a suggested route, stop early, or run without a network route. Never infer a claim from the planned distance or route polygon. | Server response metrics are recomputed from submitted samples. Planned and free runs with the same trace produce the same validation outcome. | Should planned-route completion earn a separate non-territory result? Which route provider and routing terms are acceptable? |
| GPS quality and sample count | Keep current accuracy ceiling of 30 m, strict increasing timestamps, 30 s maximum sample gap, and 12 m/s segment speed as provisional plausibility filters. Require enough samples to form a simple ring; calibrate sample spacing on devices before fixing a minimum. | Reported accuracy, coordinates, and timestamps are client-controlled. Speed checks can reject GPS drift but cannot prove physical presence. Large gaps, urban multipath, tunnels, poor fixes, and app suspension can cause rejection. | Reject invalid ranges, non-finite values, out-of-order time, over-limit gaps, and implausible jumps with stable reason codes. Device fixtures around each boundary are approved before rollout. | Confirm accuracy and speed thresholds, gap policy, and whether stationary periods are retained or removed. |
| Distance | Calculate path length server-side from accepted samples using one documented geodesic calculation. Keep the current 100 m minimum provisional; do not accept a client distance. | GPS noise can inflate path length. Sparse interpolation is unsafe and may invent movement. No server clock or signed sensor feed currently authenticates sample timestamps. | Client distance fields have no effect. The same trace yields the same server distance and eligibility. Samples across a gap are not bridged for reward distance. | Choose the minimum and whether filtering/smoothing is allowed; test false rejection versus noise inflation on consented traces. |
| Loop closure and area | For an initial claim prototype, require a closed simple loop. Current 50 m closure and 50 m² area are provisional candidate values inherited from web behavior, not approved rules. Compute the polygon and area on the server from the trace. | A large closure allowance may create a long artificial closing edge and area. Near-self-touching loops, GPS jitter, antimeridian paths, and high latitudes need defined behavior. Reject self-intersections and invalid projection cases. | No client polygon, area, perimeter, or reward changes the result. Test just below/at/above chosen closure and area values and reject self-intersecting geometry. | Must claims require loops? Confirm closure tolerance, minimum area, projection/coordinate precision, and handling of the closing edge. |
| Straight or back-and-forth paths | Do not award an instant territory from an open line or repeated out-and-back trace. Allow such routes to count toward a future progression system only after the target area and progress unit are approved. This prevents a trivial line from enclosing fabricated area. | A route that retraces itself can have high distance but near-zero unique coverage. A client cannot submit an arbitrary polygon as proof. | Open or zero-area routes never create a territory. A future progress rule must be based on server-derived path coverage and cannot multiply repeated distance into unlimited rewards. | Decide whether line exploration has value, and how progress is visualized without an elaborate grid. |
| Geometry and self-intersection | Derive one simple polygon from the accepted loop for v0. Reject self-crossing traces. Avoid a grid/cell system unless playtests show it is required. | Current projected segment checks are quadratic in vertex count and include touch/collinear rejection; global overlap tests are absent. Geometry around the antimeridian/high latitudes has not been validated. | Bounded trace sizes and deterministic topology checks; invalid rings do not mutate map or counters. Add geographic edge fixtures before supporting those regions. | Select supported geographic range and whether future route simplification is allowed. |
| Repeated and parallel paths | Later, accumulate progress only from newly covered path corridor area within a defined candidate region. Repeated passes over the same corridor should saturate rather than count forever. Parallel passes may extend coverage only when separated by more than the GPS uncertainty band. | Coverage width derived from GPS accuracy can be gamed because accuracy is client-reported. Any progress ledger must be server-authoritative, idempotent per activity, and resistant to replay. | Replaying one activity adds zero progress; repeated identical paths saturate; parallel paths add only bounded, geometrically new progress; a processed activity has one immutable receipt. | Define corridor width, saturation, progress unit, maximum progress per activity, and how a candidate region is chosen. |
| Permanent claim versus upgrade | First valid loop creates a claim. Until an upgrade mechanic is approved, later activity must not silently change area, strength, or ownership. If approved, require an explicit progress threshold and return an upgrade receipt separate from a first-claim receipt. | The current `strength` value is set from area, but no meaningful upgrade behavior exists. Mixing path length, area, and strength creates unclear incentives and exploitable units. | First claim and upgrade outcomes have distinct statuses and server-derived before/after values. Unsupported repeat activity cannot mutate existing territory. | Define upgrade stages, thresholds, caps, and whether strengthening protects against attacks. |
| Overlapping and simultaneous claims | Proposed v0: reject a candidate if it overlaps an existing owned territory above a Product-selected tolerance; when two candidates conflict, a database-backed spatial reservation/conflict rule chooses one winner deterministically. Do not let request timing silently create overlapping ownership. | There is currently no overlap check or spatial reservation. Mongo transactions serialize writes but do not by themselves prevent two different activities from claiming intersecting polygons. Map reads may be stale. | Concurrent intersecting claims yield one deterministic accepted claim and one explicit conflict rejection; no overlapping duplicate ownership beyond the chosen boundary tolerance; counts match ownership. | Choose overlap tolerance, boundary-touch policy, winner policy (first committed, earliest server submission, or another rule), and whether allied teams may overlap. |
| Ownership transfer and attacks | Defer attacks. Existing mutation code supports an internal evidence-gated transfer, but no trusted attack evidence producer or live eligibility rules exist. When designed, an attack must be a separately validated activity and transactionally replace owner and recount both owners. | Never accept client attack distance. Team cleanup currently clears `teamOwner`; no active Team model collection exists. A stale attack against changed ownership must fail. | Attack UI/API remains disabled until the server computes eligibility, owner transfer, idempotency, transaction rollback, and map result in isolated tests. | Define attack route/boundary relation, eligibility, cooldowns, minimum progress, defenses, ties, and team ownership. |
| Duplicate/replay prevention | Require an owner-scoped client activity key and immutable server activity ID; use idempotent submission and mutation receipts. Exact trace fingerprints are a useful replay filter, not proof of a real run. | Altered timestamps evade exact fingerprint matching; another device can synthesize a plausible trace. The server currently trusts device time and GPS values as plausibility evidence. | Same activity retry returns the durable state/receipt and never awards twice. Exact identical trace under a new key is rejected. Altered/fabricated trace risk is explicitly accepted only for a limited pilot or mitigated further. | Decide whether device attestation, signed platform location, anomaly review, or a limited fraud tolerance is required. |
| Persistence, decay, and seasons | Proposed v0: ownership is permanent until an approved attack or administrative correction. Territory map visibility should match that persistence. Do not infer decay from the current seven-day map query. | Current `/territories` returns only territories with timestamps newer than seven days even though the documents and counters persist. This makes ownership disappear from the map after a week. | An owned territory remains visible for the same period it remains owned; map result after restart matches database state. | Choose permanent, seasonal reset, decay, or archive semantics; define season boundary and user notice before implementing expiration. |
| Rejection and pending UX | Use stable machine-readable reason codes and plain-language messages. `submitted`/`accepted` but not yet committed is pending; only a durable processed claim is success. A failed upload keeps a retryable local draft. | The mobile app currently marks fewer-than-four samples rejected locally without submitting a server rejection; summary fallback can say “RUN COMPLETE” when no explicit outcome is present. A lost response after commit must recover by retrying the same ID. | No pending, rejected, or unknown state renders “territory acquired.” Every rejection maps to a documented reason; retry returns the same durable outcome. | Approve user-facing copy and whether rejected raw traces remain available for appeal/debugging. |
| Privacy and retention | Keep raw GPS private and collect only with clear location consent. Propose configurable short retention with deletion/export and access controls before launch. Public map responses should expose only geometry needed for play. | Raw Activity samples are retained indefinitely. `/territories` returns full territory geometry/path data. Location traces can reveal home/work and routines. | Access-control and deletion tests cover raw evidence; public map response contains no raw activity trace or unnecessary path points; retention is enforced and audited. | Choose retention period, start/end masking, public boundary precision, consent copy, and deletion behavior. |

## Release rule

The existing verifier implements a specific closed-loop claim mechanic with 50 m closure, 100 m path distance, 50 m² area, 30 m accuracy, 30 s gap, and 12 m/s speed limits. This is an active prototype rule set only. Product must approve or revise it before those values are treated as launch behavior. Until overlap arbitration and MongoDB transaction behavior are tested against an isolated replica set, claims should not be enabled for a public release.
